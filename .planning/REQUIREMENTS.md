# Requirements

## Requirements

Requirement markers: `[ ]` is open, `[x]` is complete, and `[/]` is accepted as complete for compatibility.

- [x] **REQ-001** — Managed commands retain a real terminal on stdin, stdout, and stderr while the complete initial-command log and exit code remain durably inspectable after completion. (milestone: v1.1-agent-dispatch) (depends: none) (evidence: deterministic tmux integration test proving TTY detection, first/last output capture, and exit-state recording)
- [x] **REQ-002** — Pi exposes a separate `tmux_agent` tool that launches supported `pi`, `claude`, and `hermes` backends through the existing owned-pane job lifecycle using backend-appropriate interactive and headless commands. (milestone: v1.1-agent-dispatch) (depends: REQ-001) (evidence: extension invocation tests with fake backend executables asserting command construction, mode selection, and owned job discovery)
- [x] **REQ-003** — Pi and Claude prompt bytes are transported through an owner-only file or stdin and do not appear in child process arguments, tmux pane metadata, `command.sh`, or `metadata.json`; Hermes one-shot dispatch is the documented exception because its `-z` interface places the prompt in argv. (milestone: v1.1-agent-dispatch) (depends: REQ-002) (evidence: sentinel prompt tests inspect live argv and persisted artifacts for every backend and prove the Hermes exception is surfaced in the tool contract and launch result)
- [x] **REQ-004** — Adapters preserve each CLI's native permission behavior and never add explicit permission-bypass flags; Hermes dispatch prominently reports that native `hermes -z` execution auto-bypasses approvals. (milestone: v1.1-agent-dispatch) (depends: REQ-002) (evidence: adapter tests assert generated arguments and the Hermes dispatch warning for tool results and documentation)
- [x] **REQ-005** — Interactive agent launches remain attached to a genuine tmux PTY and can be observed, taken over, sent input, interrupted, waited on, and closed through the existing job controls. (milestone: v1.1-agent-dispatch) (depends: REQ-001, REQ-002) (evidence: live tmux integration lifecycle for deterministic Pi, Claude, and Hermes fake agents)
- [x] **REQ-006** — Explicit dispatch launches return control immediately and deliver exactly one bounded completion notification to the originating live Pi session with backend, job identity, exit status, and an inspection path; reload or shutdown leaves no stale notifier. (milestone: v1.1-agent-dispatch) (depends: REQ-002) (evidence: deterministic extension lifecycle tests for success, failure, reload, shutdown, and duplicate suppression)
- [x] **REQ-007** — Existing `tmux_job` ownership tagging, output bounds, duplicate-name rejection, running-job close protection, explicit force semantics, and generic command behavior remain compatible. (milestone: v1.1-agent-dispatch) (depends: none) (evidence: unchanged legacy integration suite plus targeted regression assertions after the logging refactor)
- [x] **REQ-008** — A fresh package install documents and exposes the generic job tool and agent launcher with supported backends, model routing, configuration inheritance, privacy boundaries, the Hermes one-shot approval exception, dispatch semantics, and explicit non-goals. (milestone: v1.1-agent-dispatch) (depends: none) (evidence: fresh-install discovery test, manifest assertions, and reader-facing README review)
- [x] **REQ-009** — `tmux_agent` accepts exact Pi `provider/model` identifiers and supported thinking levels, validates them against Pi's live model registry before launch, and therefore routes GPT and local LiteLLM models such as `litellm/deep`, `litellm/deep-think`, and `litellm/fast` through Pi rather than Codex CLI. (milestone: v1.1-agent-dispatch) (depends: REQ-002) (evidence: fake-registry tests for valid, missing, and ambiguous models plus live smoke validation against the installed Pi registry)
- [x] **REQ-010** — Hermes launches inherit the operator's normal Hermes configuration, rules, memory, skills, and plugins unless the operator explicitly supplies supported overrides; the adapter does not inject isolation flags. (milestone: v1.1-agent-dispatch) (depends: REQ-002) (evidence: adapter argument tests and an isolated HOME integration fixture proving native configuration loading is retained)
- [x] **REQ-011** — An operator-level `PI_TMUX_JOB_MAX_LOG_BYTES` policy accepts a positive byte limit that keeps each job's cumulative retained terminal-log footprint within that limit throughout sustained execution while preserving the newest output in chronological order; unset or `0` retains v1.1's unlimited behavior, and the LLM-callable tools cannot override the policy. (milestone: v1.2-log-resilience) (depends: none) (evidence: real-tmux sustained-output tests repeatedly sample all retained log segments during execution and prove capped, uncapped, invalid-value, and oversized-write behavior)
- [x] **REQ-012** — Capped logging preserves genuine command PTYs, logger-drain-before-exit semantics, exit codes, inspection paths, and existing job controls while clearly recording and reporting when older output was discarded. (milestone: v1.2-log-resilience) (depends: REQ-011) (evidence: integration regression tests prove TTY/exit/drain behavior plus truncation metadata, tool output, packed-package discovery, and README contract)
- [x] **REQ-013** — Repeated small writes that cross the configured cap multiple times retain a byte-exact chronological suffix equal to the newest `maxBytes` of the complete input stream, while preserving cap, truncation-marker, and drain guarantees. (milestone: v1.2.1-tail-verification) (depends: REQ-011) (evidence: deterministic direct-writer test feeds distinct delayed chunks through multiple over-budget rewrites and compares the final file byte-for-byte with the concatenated input suffix)
- [x] **REQ-014** — A dispatch completed by a real tmux child delivers exactly one `tmux-agent-completion` custom message into its originating live Pi `AgentSession`, triggers exactly one follow-up model turn, and produces no late message or turn after session shutdown. (milestone: v1.2.2-live-completion-proof) (depends: REQ-006) (evidence: deterministic SDK integration test uses Pi's real AgentSession/extension/tool pipeline with a scripted faux model and fake child executable to assert tool execution, custom-message ingestion, follow-up turn count/content, exactly-once quiescence, and shutdown suppression)
- [x] **REQ-015** — Every `tmux_agent` dispatch records and reports its resolved Git repository root, current worktree root, branch or detached revision, dirtiness, and declared read/write intent without changing generic `tmux_job` behavior or breaking historical job metadata. (milestone: v1.3-workspace-safety) (depends: REQ-007) (evidence: unit and real-extension tests cover repositories, linked worktrees, detached/non-Git directories, persisted metadata, status output, and legacy records)
- [x] **REQ-016** — Workspace `auto` policy serializes allocation decisions, permits read-only sharing, uses a clean unoccupied worktree for a sole writer, creates isolation for concurrent writers, and fails closed for dirty or otherwise ambiguous write targets unless the caller explicitly selects the current tree. (milestone: v1.3-workspace-safety) (depends: REQ-015) (evidence: deterministic concurrency and policy matrix tests prove same-tree writer isolation, cross-repo independence, read sharing, dirty-tree refusal, and explicit-current behavior)
- [x] **REQ-017** — Managed worktrees are created from the requested repository revision under an operator-owned root with collision-safe branches and external ownership records, while uncommitted source-tree changes are never silently copied or discarded. (milestone: v1.3-workspace-safety) (depends: REQ-016) (evidence: temporary-repository integration tests prove branch/base/path identity, permissions, ownership records, dirty-source handling, and launch-failure rollback)
- [x] **REQ-018** — Workspace cleanup is explicit, refuses running jobs, dirty worktrees, missing/mismatched ownership, and unowned worktrees, removes only verified extension-owned clean worktrees, deletes only unchanged extension-created branches, and preserves branches containing commits. (milestone: v1.3-workspace-safety) (depends: REQ-017) (evidence: temporary-repository lifecycle tests cover every refusal and preservation path plus successful idempotent cleanup)
- [x] **REQ-019** — Workspace safety is documented, packaged, and regression-tested across Pi/Claude/Hermes dispatch, genuine PTYs, completion delivery, log retention, model routing, and existing lifecycle controls, with no model-reachable destructive cleanup override. (milestone: v1.3-workspace-safety) (depends: REQ-015, REQ-016, REQ-017, REQ-018) (evidence: full gate, packed-package discovery, reader contract assertions, and independent audit)
- [x] **REQ-020** — Agent job metadata additively records backend and launch mode so live status can distinguish generic commands from Pi, Claude, and Hermes jobs without rejecting historical records. (milestone: v1.4-job-status-widget) (depends: REQ-015) (evidence: metadata round-trip and legacy-record tests across all backends and generic jobs)
- [x] **REQ-021** — A deterministic status projection converts owned jobs into a stable aggregate and bounded detail view that reports running/exited counts, job name, backend or generic-command identity, state/exit, workspace kind, and log truncation while prioritizing active jobs and explicitly reporting overflow. (milestone: v1.4-job-status-widget) (depends: REQ-020) (evidence: pure snapshot/render matrix tests for empty, active, exited, truncated, managed, overflow, and stable ordering cases)
- [x] **REQ-022** — A non-overlapping session-scoped monitor starts only in TUI mode, refreshes immediately and at a bounded cadence, updates UI only when the projected view changes, reports polling failure without notification spam, and prevents late updates after reload or shutdown. (milestone: v1.4-job-status-widget) (depends: REQ-021) (evidence: deterministic fake-scheduler lifecycle tests for immediate refresh, overlap suppression, deduplication, recovery, stop cleanup, and late-result suppression)
- [x] **REQ-023** — Pi shows a compact footer aggregate plus a bounded below-editor detail widget only while owned jobs exist; active jobs are listed first, exited jobs remain inspectable while their panes remain open, and the extension clears both surfaces on session shutdown without replacing Pi's footer or editor. (milestone: v1.4-job-status-widget) (depends: REQ-021, REQ-022) (evidence: extension-context integration tests assert exact setStatus/setWidget calls, placement, bounded lines, empty-state clearing, and session lifecycle cleanup)
- [x] **REQ-024** — Job status is documented, packaged, and regression-tested with generic tmux jobs, all agent backends, workspace safety, genuine PTYs, completion delivery, bounded logs, and non-TUI modes, with no background resource started from the extension factory. (milestone: v1.4-job-status-widget) (depends: REQ-020, REQ-021, REQ-022, REQ-023) (evidence: full gate, fresh-package contract assertions, resource-leak checks, and independent audit)
- [x] **REQ-025** — A deterministic integration test uses Pi's real `InteractiveMode` extension UI context and footer/widget components with a real owned tmux job to observe rendered running state, rendered exited state, pane-close clearing, and monitor-stop clearing without starting raw terminal input or leaking Pi/tmux resources. (milestone: v1.4.1-real-tui-status-proof) (depends: REQ-023) (evidence: real Pi InteractiveMode + real TmuxJobManager lifecycle test, full regression gate, package/docs assertions, and independent audit)
- [x] **REQ-026** — Each new job records its originating Pi pane; passive footer/widget status shows only jobs from that origin, successful exits disappear after a bounded completion interval or explicit status acknowledgment, failures remain attention-visible, and none of these visibility transitions closes the retained pane or narrows explicit session-wide management. (milestone: v1.5-parent-scoped-status) (depends: REQ-007, REQ-014, REQ-025) (evidence: manager, pure projection, UI bridge, real InteractiveMode, extension invocation, packed-package, full-gate, and reader-contract tests)
