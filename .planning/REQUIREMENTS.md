# Requirements

## Requirements

Requirement markers: `[ ]` is open, `[x]` is complete, and `[/]` is accepted as complete for compatibility.

- [x] **REQ-001** — Managed commands retain a real terminal on stdin, stdout, and stderr while the complete initial-command log and exit code remain durably inspectable after completion. (milestone: v1.1-agent-dispatch) (depends: none) (evidence: deterministic tmux integration test proving TTY detection, first/last output capture, and exit-state recording)
- [x] **REQ-002** — Pi exposes a separate `tmux_agent` tool that launches supported `pi`, `claude`, and `hermes` backends through the existing owned-pane job lifecycle using backend-appropriate interactive and headless commands. (milestone: v1.1-agent-dispatch) (depends: REQ-001) (evidence: extension invocation tests with fake backend executables asserting command construction, mode selection, and owned job discovery)
- [x] **REQ-003** — Pi and Claude prompt bytes are transported through an owner-only file or stdin and do not appear in child process arguments, tmux pane metadata, `command.sh`, or `metadata.json`; Hermes one-shot dispatch is the documented exception because its `-z` interface places the prompt in argv. (milestone: v1.1-agent-dispatch) (depends: REQ-002) (evidence: sentinel prompt tests inspect live argv and persisted artifacts for every backend and prove the Hermes exception is surfaced in the tool contract and launch result)
- [x] **REQ-004** — Adapters preserve each CLI's native permission behavior and never add explicit permission-bypass flags; Hermes dispatch prominently reports that native `hermes -z` execution auto-bypasses approvals. (milestone: v1.1-agent-dispatch) (depends: REQ-002) (evidence: adapter tests assert generated arguments and the Hermes dispatch warning for tool results and documentation)
- [x] **REQ-005** — Interactive agent launches remain attached to a genuine tmux PTY and can be observed, taken over, sent input, interrupted, waited on, and closed through the existing job controls. (milestone: v1.1-agent-dispatch) (depends: REQ-001, REQ-002) (evidence: live tmux integration lifecycle for deterministic Pi, Claude, and Hermes fake agents)
- [x] **REQ-006** — Explicit dispatch launches return control immediately and deliver exactly one bounded completion notification to the originating live Pi session with backend, job identity, exit status, and an inspection path; reload or shutdown leaves no stale notifier. (milestone: v1.1-agent-dispatch) (depends: REQ-002) (evidence: deterministic extension lifecycle tests for success, failure, reload, shutdown, and duplicate suppression)
- [x] **REQ-007** — Existing `tmux_job` ownership tagging, output bounds, duplicate-name rejection, running-job close protection, explicit force semantics, and generic command behavior remain compatible. (milestone: v1.1-agent-dispatch) (depends: none) (evidence: unchanged legacy integration suite plus targeted regression assertions after the logging refactor)
- [x] **REQ-008** — A fresh package install documents and exposes the generic job tool and agent launcher with supported backends, model routing, configuration inheritance, privacy boundaries, the Hermes one-shot approval exception, dispatch semantics, and explicit non-goals. (milestone: v1.1-agent-dispatch) (depends: none) (evidence: fresh-install discovery test, manifest assertions, and reader-facing README review)
- [x] **REQ-009** — `tmux_agent` accepts exact Pi `provider/model` identifiers and supported thinking levels, validates them against Pi's live model registry before launch, and therefore routes GPT and local LiteLLM models such as `litellm/deep`, `litellm/deep-think`, and `litellm/fast` through Pi rather than Codex CLI. (milestone: v1.1-agent-dispatch) (depends: REQ-002) (evidence: fake-registry tests for valid, missing, and ambiguous models plus live smoke validation against the installed Pi registry)
- [x] **REQ-010** — Hermes launches inherit the operator's normal Hermes configuration, rules, memory, skills, and plugins unless the operator explicitly supplies supported overrides; the adapter does not inject isolation flags. (milestone: v1.1-agent-dispatch) (depends: REQ-002) (evidence: adapter argument tests and an isolated HOME integration fixture proving native configuration loading is retained)
- [x] **REQ-011** — An operator-level `PI_TMUX_JOB_MAX_LOG_BYTES` policy accepts a positive byte limit that keeps each job's cumulative retained terminal-log footprint within that limit throughout sustained execution while preserving the newest output in chronological order; unset or `0` retains v1.1's unlimited behavior, and the LLM-callable tools cannot override the policy. (milestone: v1.2-log-resilience) (depends: none) (evidence: real-tmux sustained-output tests repeatedly sample all retained log segments during execution and prove capped, uncapped, invalid-value, and oversized-write behavior)
- [x] **REQ-012** — Capped logging preserves genuine command PTYs, logger-drain-before-exit semantics, exit codes, inspection paths, and existing job controls while clearly recording and reporting when older output was discarded. (milestone: v1.2-log-resilience) (depends: REQ-011) (evidence: integration regression tests prove TTY/exit/drain behavior plus truncation metadata, tool output, packed-package discovery, and README contract)
